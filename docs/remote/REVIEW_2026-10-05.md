## 一、发现列表（按严重度）

### 🔴 高 — 功能性缺陷（root 环境）

**F1. `LinuxGroupExitWaiter.TryReap` 用错 siginfo 字段偏移，root 下永远回收不了后代**
`modules/SourceGit.Core/LinuxGroupExitWaiter.cs:229`
```csharp
if (BitConverter.ToInt32(info, 16) == 0) return false; // No exited child was available.
```
- Linux UAPI（x86-64 与 arm64 相同，已对 `include/uapi/asm-generic/siginfo.h` 核实）布局：union 从偏移 12 开始，`si_pid @12`、`si_uid @16`、`si_status @20`。代码读的是 **si_uid（偏移 16）**，不是 si_pid。
- `waitid(P_PIDFD, WEXITED|WNOHANG)` 成功回收时 si_pid=子进程 pid（非 0）、si_uid=子进程 uid。**非 root 用户 uid≠0 → 恰好判"已回收"，功能正常**（现有 WSL 测试以普通用户运行，全部通过）；**root 下 si_uid=0 → 被误判为"没有已退出子进程"** → 成员永远不移出 `members` → 组等待永不完成 → 操作永久卡在 `terminating`，服务器无法空闲退出。
- 建议：改为判断偏移 12（`si_pid == 0` 才是"无子进程可用"；WNOHANG 无子进程时内核不写 buffer，零初始化下 si_pid=0，语义正确）。并补一个直接注入 `si_pid≠0 / si_uid=0` 字节序列的单元测试，不依赖运行用户。

### 🟠 中

**F2. 成功写操作可能因 handle 过期被报告为失败**
`modules/SourceGit.Core/RepositoryService.cs:191, 325`
```csharp
return result with { ..., Generation = ... Get(repo.Id).Generation };
```
操作运行期间若最后一个 lease 被关闭（客户端断连/关闭句柄），`Get` 抛 `KeyNotFoundException("Repository handle expired")`，**已成功的 git 写被上报为失败**。上方 `finally`（:189）已用容忍式 `TryGetValue` 处理通知，唯独返回行没有。建议 try/catch 该异常 → 回退到操作开始时捕获的 generation（或 0），并在 OperationInfo 中标注 handle 已过期。

**F3. 长操作终止时会误关整个 GUI 通道**
`modules/SourceGit.Server/Program.cs:84, 435`
`OperationOutput` 事件的 `cancellation` 是操作的 `ExecutionToken`（:84）；`SendEvent` 中 `catch (OperationCanceledException) when (cancellation.IsCancellationRequested) { connection.Client.Close(); throw; }`（:435）——慢客户端上操作被终止（超时/用户终止）时，一次在途的输出写会 **Close 整个通道**，客户端断开重连。建议：仅当取消来自通道生命周期（lifetime token）时才关通道；操作 token 的取消只丢弃该条事件。

**F4. `DrainTunnel` fire-and-forget 与 dispose 竞态 → 未观察任务异常**
`modules/SourceGit.RemoteClient/ConnectionManager.cs:186, 422-433`
`_ = DrainTunnel(_tunnel)` 无人等待；`DisposeCoreAsync` 直接 `Kill(true)` + `Dispose()` 隧道进程，drain 任务里挂起的 `ReadToEndAsync` 将抛 ODE/IOE → 未观察任务异常（丢失 stderr 诊断）。建议 `DrainTunnel` 内 try/catch 全部异常（dispose 场景静默），或 dispose 时带短超时等待 drain 任务。

**F5. `RemoteWorkspace.Connections` 只写不删**
`src/Remote/RemoteWorkspace.cs:35`（全文仅 :17/:35/:93/:98/:209 五处引用，无 Remove/Clear）
每个曾连接过的唯一 `remote:...` 路径永久保留一个旧 `RemoteWorkspace` 实例。上限=不同连接路径数（重连是覆盖而非累积），属慢泄漏而非无界增长。建议在断开/实例替换时 `TryRemove`（注意与 `TryAcceptSnapshot`/`ForPath` 的读取竞态，用 `TryRemove` 返回值判断即可）。

### 🟡 低 / 健壮性

- **F6** `ConnectionManager.cs:246`：`WaitForRecoveredClient` 硬编码 `TimeSpan.FromMinutes(5)`，而 `_recoveryTimeout`（:44/:58）在 :259 已用于恢复预算——内部构造器允许其他值时此处不跟随。建议统一用 `_recoveryTimeout`。
- **F7** `ConnectionManager.cs:147` + 重连 catch（~:268）：`Connected?.Invoke` 处理器抛出的异常被静默吞掉，无任何诊断日志。建议 catch 后 `Log(...)`。
- **F8** `RemoteRepositoryClient.ReadLoop`：`Interaction`/`RepositoryChanged` 走 `_ = Task.Run(DispatchEvent)`，绕过 4096 背压护栏，慢消费者无界。若属有意设计的独立通道，建议注释说明；否则加有界队列+丢弃策略。
- **F9** `src/Models/Watcher.cs:326-336`（`Invoke`）：refresh 回调在**持有 `_gate` 时**调用。当前安全（回调只调度异步工作），但 FSW 线程的 `MarkDirty`/`OnRepositoryChanged` 会在回调期间阻塞在 gate 上；未来任何回调若同步重入 Watcher（`Lock`/`MarkDirty`/`Dispose`）即死锁。建议"锁内检查 flags，锁外调用回调"。
- **F10** `modules/SourceGit.Contracts/GitCommandPolicy.cs`：`ls-remote`/`fetch` 允许任意 URL 参数，git 的 `ext::` 传输可执行任意命令。当前威胁模型（本机 GUI+本机 server、同一用户）下不是实际漏洞，但若 server 未来用于多用户/共享场景会成为注入点。建议显式拒绝参数中的 `ext::`（防御性，一行判断）。
- **F11** `build/scripts/publish-remote.ps1:5`：`[bool]$ClientAot = $true` 默认 AOT，但文档记录的验证交付路径是**非 AOT**（AOT 发布 exit 1、平台 linker 缺失）——默认跑脚本在这类机器上必失败。建议默认 `$false`，或文档强制 `-ClientAot:$false`。
- **F12** `modules/SourceGit.Core/WindowsJobExitWaiter.cs` `Members()`：`QueryMembers`（class 3）用裸 count+ids 缓冲 + ERROR_MORE_DATA 扩容，属非标准用法。12 个测试（含强制 1 条目缓冲）已实证通过，但建议在注释中引用 MSDN 文档（JobObject 成员列表布局）以佐证 ABI 稳定性。
- **F13** `src/Models/FetchSchedule.cs:38`：`Configure` 对非正 interval 抛异常，而计划原文是"interval 非正 → 禁用"。调用方 `Repository.ConfigureLocalFetch`（`src/ViewModels/Repository.cs:171-176`）已做 `interval > 0` 守卫+trace，实际行为正确；建议 `FetchSchedule` 自身容忍非正值（禁用）或在 XML 注释中明确前置条件。
- **F14** `ProcessLifetime`/`OperationStore`：终止只尝试一次 kill；单次 kill 失败则操作停留在 `terminating`（符合规范"阻塞+上报"）。建议加有限次 kill 重试（如 3 次×500ms）。

### 🔵 UX / nit

- **F15** 远程写（`RemoteWorkspace.ExecuteGitAsync` 传 `CancellationToken.None`，持久写设计）：用户点取消只解除等待，服务端操作继续。UI 应明确提示"已取消等待，操作仍在服务器运行"，否则看起来像取消失灵。
- **F16** `LocalServerLauncher.ObserveStartupAsync`：ready 恰在 deadline 边界到达时报"未发布 ready"（下一轮发现循环自愈）。边界条件 nit。

## 三、值得肯定之处

1. **终止协调（§6/P6）** 是本次最复杂的部分，`outcome`/`outcomeGate` 的三态设计把"超时触发终止"与"进程自然完成"的竞态处理得很干净，快速路径（树已空免杀）避免了不必要的 kill。
2. **`BootstrapEndpoint`** 对 UDS ready 端点的清理（statx no-follow、0700/0600 所有权复核、PID+starttime 防复用、SIGKILL 间隙只回收空目录）是教科书级的防御，且"启动触发、绝不周期扫描"符合最小权限直觉。
3. **§1 徽章代际** 的判定链（序列→路径→instance→repo→generation 五道闸）与 `RepositorySnapshotTracker` 的"仅同 session 内单调"语义精确匹配计划验收标准里的全部边界用例（新 instance gen=0、session 重建、乱序回包、取消）。
4. **测试证据可复核**：`GitCommandPolicy` 的动词/旗标白名单与 `IsQuery` 双表、`measure-remote-polling.ps1` 的交错采样与哈希校验，都让"文档声称的 4096/4097 压力测试"可信。

## 五、核验与整改记录（2026-10-05）

本次先核验判断，再完成 F2/F3/F4/F5/F6/F7/F11/F13 的整改，补充 F1/F12 的 ABI 依据。没有新增常态轮询。arm64 按用户明确要求不做运行测试；Windows Native AOT 仍未验证。

| 意见 | 当前结论与处理 |
|---|---|
| F1 | **原结论不成立，保持 PID 偏移 16。** 64 位 union 有八字节对齐，三个 int 后存在四字节 padding；不能直接使用三个 int 的长度作为 union 偏移。WSL x64 C `offsetof` 输出 `pid=16 uid=20 status=24 size=128`。新增 PID 非零/UID 零和 PID 零/UID 非零两组字节验证；实际 Linux 进程树检查以普通用户、root 各运行 15 项，退出均为 0。 |
| F2 | **已修复。** Git 和自定义命令返回结果时使用 `TryGetValue`，会话已关闭则回退到执行前捕获的 generation。PrepareProcess 屏障让最后一个 lease 在实际执行前关闭，两类真实 Git 写均成功持久化并正确返回；不增加 wire 字段或把成功写改成失败。 |
| F3 | **已修复，按完整帧边界取消。** 排队/准入使用操作 token，帧一经准入则用独立通道写预算完成；取消排队事件不会关闭共享通道。已发出帧头后不能直接丢弃帧体，否则下一 RPC 会被当作上一帧内容。只有通道写预算耗尽、可能留下不完整帧时关闭通道。协议屏障与真实 server 下一 RPC 两层回归通过。 |
