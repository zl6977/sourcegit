# Windows client and Linux server deployment

The Server runs as the selected WSL/SSH user. It requires Linux **5.4+**, x64 or arm64, Git, POSIX sh, tar, sha256sum, flock, util-linux setsid and nohup, plus the native dependencies of a self-contained .NET 10 application (glibc, libstdc++, ICU, OpenSSL and zlib). Remote environment preflight checks the kernel release; native pidfd/waitid support is checked before starting Git commands. A kernel or security policy that blocks these facilities is rejected rather than falling back to periodic tree scans. It does not require a separately installed .NET runtime. Windows needs wsl.exe for WSL and OpenSSH for SSH.

Windows development execution attaches containment immediately after Process.Start. Stable member waits and authoritative zero-active-process accounting cover members assigned to that Job; descendants created before assignment are outside that confirmed boundary. Member-query or wait-registration failures preserve cleanup ownership and report failure rather than declaring the tree empty. Native cleanup fault/resource evidence is recorded separately from Linux production acceptance.

Linux cleanup treats a tree as empty only after the managed root has exited and the group is confirmed absent. Unreaped zombies retain cleanup responsibility; pidfd registration/reaping failures preserve it for subsequent authoritative recovery. The 4096 live-member watch limit is an upper bound, subject to the host's open-file/process limits. Default test-host soft FD limit 1024 cannot accommodate that entire set. Full pressure verification used an isolated shell with FD limit 8192, without changing normal host/service limits; administrators choose service limits for their intended concurrency.

## Bootstrap notifications in the current worktree

Server repository file events use a one-shot 200ms debounce capped at two seconds from the first dirty event, so continuous changes cannot indefinitely delay RepositoryChanged. Watcher errors request an immediate full refresh. Events arriving during notification form a following batch; closed sessions stop scheduling. Failed notification consumers retry pending work after one second and stop after success. This is event-driven scheduling, with no recurring check for idle repositories.

Canceling an operation's output before frame admission drops the event without closing the shared channel. After admission the whole frame must finish under a separate bounded channel write deadline; a partially written frame cannot safely be discarded. Closing the final repository lease does not retroactively fail a successful persistent write. Recovery waiters share the worker's recovery budget and cancel only their own wait. Nonpositive local auto-fetch intervals disable scheduling and invalidate queued callbacks.

The previous controlled WSL comparison measured first-start median 270.84 ms to 353.15 ms (about +82 ms), while graceful upgrade improved. These are workload-specific historical samples; the review fixes were checked for correctness without rerunning that performance comparison. No general startup or idle-CPU improvement is claimed.

GUI Trace records watcher degradation entry/recovery, monotonic elapsed time, failed-source/fallback counts and the next fallback delay. Server stderr records repository-notification and channel-close retry failures/recovery with timestamps, attempt counts, exception types and next delays. Repeated failures are coalesced at attempts 1, 2, 4, 8 and later powers of two, with a summary on recovery; raw exception text and connection credentials are omitted. These diagnostic events do not create periodic idle work.

The permitted elapsed/relative-time display timers run only for loaded, visible controls whose ancestors are visible and whose window is not minimized. Ancestor/window property notifications stop and resume scheduling; unloading removes subscriptions. Completed command logs and absolute commit dates remain stopped after restoring a page/window.

Opening a remote repository in the GUI has a relative 90-second connection budget. Only actual transient I/O/socket failures retry, with a two-second delay and at most three restore attempts; that same budget cancels the delay. Non-transient errors report immediately. Retry Trace diagnostics record time, exception type, attempt and delay; they omit raw exception text. The same path cannot be opened concurrently, and finalization releases that admission on success or failure.

Unexpected disconnection uses one relative five-minute recovery budget covering connection attempts and failure backoff. Caller cancellation ends only its own shared recovery wait. When the budget expires before installation, waiters receive an explicit unknown-operation-outcome failure; a manual retry creates a fresh recovery generation. A verified client already installed/published is the authoritative successful result and is not downgraded by a later consumer callback error or deadline. Manager disposal cancels pending recovery waits and joins in-flight installation.

Local development startup separates cancellation of the connection wait from ownership of an already spawned process. Caller cancellation returns promptly; the owned startup retains the decision lock and output/process handles while its existing ten-second ready/exit observation finishes. ConnectionManager Dispose joins that observation, so complete disposal may wait for the remaining startup budget; it never kills the independent Server. A new manager can acquire the decision lock afterward and discover the published original instance, or follow the persistent identity rules below if publication is still pending.

Persistent identity protects timeout/crash paths using `<record>.startup.pending`, created before spawn and atomically bound to the child PID/start identity. It contains no connection credentials. If record publication is delayed, a subsequent launcher subscribes to file notifications and the verified process's native exit, within its ready budget. Timeout preserves the intent/child and refuses to spawn a successor. Verified child exit or exact authenticated recovery permits corresponding intent cleanup. PID/start mismatch never authorizes signaling another process.

If the launcher dies between creating the intent and binding its child, the child identity is unknown. Startup fails explicitly and preserves that intent; an original server that subsequently publishes a usable record can still be authenticated. Unknown metadata is not automatically cleared. For manual recovery, first finish operations and use the matching client to shut down any known instance, confirm relevant processes have exited, then remove only the identified `.startup.pending` file. Owner process exit alone does not prove child exit. Server ready output tolerates an already closed startup pipe, so GUI failure does not terminate a successfully initialized independent server.

Published servers carry `sourcegit-bootstrap.version` (currently 1). Installation checks this capability before invoking bootstrap; legacy archives without it are rejected rather than invoked with an unsupported subcommand. Protocol/build pairing remains mandatory. The current protocol 3 prototype archive under `artifacts/bootstrap-prototype` is development verification, not the final release package.

Current protocol 3 development binaries also passed actual Windows OpenSSH lifecycle checks against a private loopback sshd in WSL: production installation/tunnel, rejected active-write shutdown, same-instance recovery without replay, immutable successor startup and confirmed native exit. This transport check does not replace the final release-pair, standalone host or arm64 acceptance gates. See TEST_RESULTS.md for the archive digest, initial fixture failure and credential/daemon cleanup evidence.

The startup shell obtains the host `start.lock` with a bounded 60-second blocking flock wait, then invokes the installed server's bootstrap once. Bootstrap creates a user-only Unix socket endpoint before launching the server with detached session, stdin and log streams. Ready carries instance/PID/nonce; bootstrap verifies the record and child identity, then checks cancellation before publishing its reply. The server keeps running when bootstrap finishes or its transport disappears. Endpoint paths bind record identity, launcher PID/start identity and a random nonce; directory/socket/owner-file permissions are 0700/0600/0600, with an exclusive owner lock. Native statx verifies UID/type/permissions before child startup; blocked ownership facilities fail explicitly.

On a later bootstrap, same-record endpoints are reconciled once within the startup deadline. Only confirmed exited launchers with current-user ownership, private permissions, valid names, no symlinks/unknown entries and an available exclusive lock are reclaimed. An empty directory left between mkdir and owner-file creation can be reclaimed using its verified dead launcher identity. Live launchers, other Unix users and legacy/unknown ownership are preserved. Reconciliation never recursively deletes directories, alters server records or kills a published child. A child may reclaim its exact endpoint after abrupt bootstrap loss; normal bootstrap disposal also cleans it. No recurring endpoint scan is added.

An authenticated upgrade captures the old process start identity during discovery and sends Shutdown from the client. One successor bootstrap waits on the old process's pidfd, then launches and awaits ready; it does not repeat startup scripts or poll record/PID state. The individual exit-wait facility requires [Linux 5.3+ pidfd support](https://man7.org/linux/man-pages/man2/pidfd_open.2.html), while the Server as a whole requires **5.4+** for descendant reaping through waitid(P_PIDFD). Unsupported or blocked notifications report failure. Socket EOF alone never authorizes replacement. Normal ready is bounded at 10 seconds; the host's old-exit + ready path at 15 seconds, with the client's existing 15-second upgrade deadline also applying.

WSL x64 prototypes and basic immutable/active-refusal/graceful-upgrade checks pass. Native bootstrap fault checks now cover incorrect ready identity, lost ready/deadline, ready versus exit, cancellation after endpoint/spawn/publication/ready, and SIGKILL before child creation with safe stale-endpoint reconciliation; published servers remain independent. Actual SSH transport loss, arm64 and final package acceptance remain unverified. SIGHUP/SIGTERM cancellation wakes the bootstrap wait without killing the server.

## WSL connection

Select a WSL 2 distribution and optional Linux user. The startup command explicitly selects both, uses noninteractive `sh`, and connects to the Server's random loopback port through WSL localhost forwarding. A failed localhost connection reports a networking error and does not enable a public listener. NAT and mirrored mode must each be validated on a host configured for that mode.

Optional environment initialization is read from `~/.sourcegit-server/server-env-setup`. This is a Bourne shell script, sourced before Server launch. It can export PATH, proxy variables and an existing SSH agent socket. It must not depend on interactive shell prompts. Startup logs are in `~/.sourcegit-server/server-<build-id>.log`; do not put secrets in that script's diagnostic output.

## SSH connection

Use an SSH Host alias from the Windows OpenSSH configuration (a plain `host` or `user@host` also works). Key/agent authentication is the default; ProxyJump and other host settings from `~/.ssh/config` still apply, and the per-connection **Extra SSH options** field appends command-line options (`-o KexAlgorithms=…`, `-p port`, `-i key`, …) that outrank the system config. The **Remote user** field is sent as `-l` (it wins over a user embedded in the target; on Windows a missing user would otherwise default to `DOMAIN\username`). Two password modes exist for hosts without keys: a **stored password** (encrypted with Windows DPAPI in the connection profile, plaintext never on disk; every ssh process of the connection signs in silently via an injected askpass, the first host key is accepted automatically, later changes still fail) and **terminal login** (OpenSSH's own prompt in a console window; each ssh process authenticates on its own, so expect a prompt per stage). Host key verification is retained in key mode. Repository Git authentication runs independently on the Linux host.

The Server binds loopback only. A separate `ssh -N -L` process forwards a local loopback port to it; startup command output is not the business protocol. The handshake verifies the expected instance ID so a load-balanced SSH alias cannot silently connect to a different host.

## Recovery and server lifetime

Each successful OpenRepository reply contains two identities: **Id (RepositoryId)** identifies the shared repository session for queries/events/snapshots; **LeaseId** identifies only that individual open. CloseRepository's IdRequest.Id is the LeaseId in v2. Concurrent or repeated closes of that lease atomically release it once; expired/unknown lease IDs are successful no-ops, and a live lease owned by another GUI owner is rejected. There is no RepositoryId fallback that decrements a shared reference.

Leases belong to the authenticated owner within their server instance. They remain valid across channel disconnects and same-owner recovery, until explicit close, owner takeover with no live channel/operation, or instance exit. They have no time-based expiry that could evict a long-running borrower. The server stores at most 4096 live leases and keeps no history of released IDs; close releases capacity. A lost Open reply can consume a lease until owner/instance cleanup, so this limit also bounds unacknowledged opens.

The workspace queues any failed close, including failures while still connected. A rebind processes each queued entry at most once in a finite batch and retains failed entries for later retries; rebinding the same connected client also drains the queue. Old-instance entries and late releases are discarded without being sent to a different instance. Close acknowledgement loss can therefore be retried safely while another lease of the same repository continues to query and watch.

Each client RPC has a ten-minute default wait deadline, including sending the frame and waiting for its ordered reply. `RemoteRepositoryClient` can receive a different deadline through its optional `rpcTimeout` constructor argument. Internal expiry reports the method and deadline as a TimeoutException; caller cancellation and connection closure retain their own semantics. This deadline does not terminate a persistent server write. On a write acknowledgement timeout the client queries the original operation id, never repeats the write, and retains an unresolved operation identity if its result query also times out. Refresh repository state before deciding whether to retry an unknown result manually.

Ordered output/completion events and operation reply barriers share an application backlog limit of 4096 queued entries. A consumer exceeding that limit fails the channel and pending requests so recovery can resynchronize; successful replies never bypass preceding output. Consumer callbacks should be brief and nonblocking. Client disposal cancels delivery and waits at most one second for its event-consumer task; an already-running callback must still return on its own.

After an authenticated Shutdown is accepted, ConnectionManager clears its public Client and detaches the old client before disposing it. The manager remains outside Connected while starting and synchronizing a validated replacement. A refused upgrade preserves the existing connected client. Callers must continue to check State and handle connection/disposal races.

The GUI process has one owner identity and recovery secret. Multiple connections from that GUI may attach to the same Server. A different GUI is rejected while the owner has a live channel or an operation is active; once both are absent it can take over immediately. The default five-minute grace, configurable through `SOURCEGIT_GRACE_SECONDS`, applies to idle exit and helper interaction waits.

Git writes, filesystem mutations and custom commands share a client operation tracker with client-generated IDs. Reconnection queries those IDs; it does not repeat writes automatically. An instance restart returns an unknown outcome even if the replacement instance happens to contain the same operation ID, so repository state must be refreshed before a user retries. Repository snapshots likewise compare generation only within the same instance and repository handle. Editor/askpass waits use operation-specific helper credentials and expire at the configured grace. Pending editor/credential requests are cached until UI handlers are attached after reconnect.

Closing the GUI disconnects its channels. Persistent writes continue independently of that connection. The authenticated `Shutdown` API atomically refuses shutdown while writes, interactions or termination cleanup are active and stops accepting new operations once shutdown is approved. Packages install into immutable `~/.sourcegit-server/versions/<build-id>/<package-sha256>/` directories by renaming a complete staged directory. An upgrade authenticates to the existing instance and requests Shutdown; an occupied instance or active operation blocks the upgrade without terminating it. Once it exits, the client starts the installed package. Rollback uses the matching older Client and package; older directories remain available.

Server write execution defaults to one hour, independently of the client's RPC deadline. Set `SOURCEGIT_OPERATION_TIMEOUT_SECONDS` in the server environment before startup to a positive number of seconds (maximum 4294967; fractional values supported). The deadline includes repository-lock waits, standard input, Git/custom execution and output cleanup. Helper waits use the shorter applicable execution/grace limit. Long clone/fetch/custom operations may need a larger configured value. A channel disconnect or caller cancellation does not shorten a registered write's server execution deadline.

At expiry the operation enters `terminating`, which continues to block shutdown, idle exit and owner takeover. The server terminates its contained process tree, drains output and reaps processes before publishing failure and releasing the repository lock. Windows uses a Job object attached immediately after process startup; Linux requires util-linux `setsid`, uses a separate process group and reaps adopted descendants. Deliberately detached descendants and Windows children spawned before job attachment are outside this containment guarantee. Failure to terminate or verify cleanup keeps the operation active and exposes the latest bounded diagnostic. Synchronous filesystem calls may not be interruptible; they remain active until they return, and an actually completed write retains its successful result.

Windows normal tree cleanup waits on stable Job-member process handles and rechecks authoritative membership after exit notifications. Linux waits on stable per-member pidfds, reaps only adopted descendants with waitid(P_PIDFD) after .NET owns root exit, and rechecks the process group after member exit/HUP notifications. Neither platform performs the former normal 20ms cleanup loop; root exit or pipe EOF alone does not release the repository lock. Already-empty Linux groups avoid /proc enumeration and waiting threads. Linux blocking waits are limited to 64 concurrent dedicated resources and 4096 live-member watches per group; queued cleanup retains operation ownership, and dead adopted members are reaped individually before applying the watch limit. Actual cleanup-facility failures retain `terminating` and retry from 500ms up to a 5s cap; the operation deadline still cancels execution if a facility failure occurred before expiry. This backoff is distinct from normal exit waiting.

The desktop avatar queue is event driven and capped at 1024 queued/active requests, with one pending UI publication. Downloads have a two-second total deadline and an 8 MiB response cap. Queue saturation defers that display request until a later request; duplicate emails share ownership. Local avatar selection and force-refetch invalidate older downloads, which cannot overwrite their cache. Desktop exit cancels and joins the consumer without requiring UI callback progress, then drains the queue. These limits apply to local GUI resources rather than remote write operations.

Clients retain unresolved writes across their manager's channel replacements, capped at 1024 records and 16MiB of serialized UTF-8 requests. Capacity is checked before submitting a write; existing unknown records are preserved. `PendingOperations` exposes the original instance and confirmation state. Same-instance `GetOperationAsync` and completion notifications confirm outcomes; reused IDs in a successor instance do not confirm old writes. `Operations.Forget(id)` explicitly acknowledges and removes a local unresolved record after its caller has stopped waiting; it does not cancel or replay the write. Query and inspect partial repository changes before acknowledging uncertainty. A wait-lane failure does not erase an accepted write's identity.

Termination performs no rollback and does not delete Git lock files. A deadline failure warns that partial writes and lock files may remain; the server publishes repository refresh notifications after successful or failed write execution. Inspect refreshed state before explicitly retrying. Reconnection only queries the original operation id; it never resubmits the timed-out write. If output sending is interrupted by the deadline, that channel is closed to avoid reusing a partially written protocol frame, and normal query-only recovery applies.

## Cleanup and diagnosis

Directory browsing creates a short-lived snapshot on the first `ListDirectory` request (offset zero, no cursor). Later requests supply the returned `DirectoryCursor` and `NextOffset`, using the same path and channel. Pages use the collected membership and metadata; additions/removals after collection appear only after an explicit refresh, while entries changing during initial collection are not an atomic filesystem image. Final pages return no cursor and reclaim the snapshot, including exact multiples of the page size. `ReleaseDirectory` is idempotent and channel-scoped. `DirectoryPagesAsync` releases its cursor when canceled or disposed early; the workspace and browser use this iterator. Expired or foreign cursors report a refresh error, without silently creating another snapshot.

Directory snapshots expire after 60 seconds from creation and are released on channel disconnect. The server caps retained snapshots/builds at 16 slots, entries at 100000 and the conservative byte budget at 16 MiB per snapshot and 64 MiB across retained snapshots. Outstanding enumeration tasks keep their build slot until they unwind even if their channel disconnects, bounding concurrent transient builders (at most 16 individually capped builds). Capacity errors ask the caller to close another listing, choose a smaller directory or refresh later. Filesystem calls may block until the OS returns; cancellation is checked between entries and before/after sorting. If a first-page reply is lost before its cursor reaches the client, TTL or disconnect provides reclamation. This is a browse-session snapshot, not a long-term directory cache.

For the Local DLL/executable development path, clients serialize discovery and startup with a separate `<canonical-record-path>.startup.lock` (60-second cancellable acquisition). Compatibility with existing FileShare.None holders requires bounded contention backoff of 250, 500, then at most 1000 ms; native byte locks cannot subscribe before an exclusively shared file can be opened. The server continues to hold its own `.lock` for its lifetime and never waits for the client's startup lock. Startup awaits the single stdout ready consumer or stable process exit within ten seconds and captures bounded stdout/stderr diagnostic tails. Persistent startup intent protects missing records after timeout or launcher failure. Manual starts do not take the decision lock. If a manual Server already holds the lifetime lock without a record, the launcher subscribes before checking, waits for record notification within its ready budget and authenticates the published instance; it does not start a competing child. Unknown manual PID/absent publication at timeout is reported conservatively. The server lifetime lock still provides final exclusion if a noncooperating manual start races the probe itself.

Local discovery retries a failed probe three times with one-second backoff. A live PID with unavailable probes is preserved and reported with PID, port and exception type. A changed record is rediscovered; only an unchanged record whose PID is confirmed dead can be deleted under the decision lock. Unreadable records are preserved. Server exit additionally verifies the stored instance and PID before removing its record. External record editing does not participate in the decision lock and is outside the atomic discovery guarantee.

A Local upgrade requires an authenticated, ownership-checked handshake and accepted Shutdown, followed by confirmed old-process exit before starting a successor. Shutdown/exit waiting is bounded at 10 seconds and cancellable. Strict protocol/build compatibility remains mandatory: if a different build cannot safely handshake, Local reports manual intervention and keeps its live process/record. Do not delete an unavailable live instance's record to force replacement.

Keep repositories intact. After all clients have disconnected, all Git operations have ended, and the Server has exited, an administrator may remove a specific unused `~/.sourcegit-server/versions/<build-id>/` directory. Complete uninstall removes only `~/.sourcegit-server/` after those conditions are met. Do not delete a running version, instance record or lock to force ownership takeover.

Instance records contain a connection token and are mode 0600 on Linux, inside the mode 0700 server directory. Do not attach those records to bug reports. Logs and connection-state messages can be shared after checking environment-script output for secrets. Include the build ID, WSL distribution or SSH alias, architecture, Git version and the failed connection stage.

Actual acceptance evidence belongs in `TEST_RESULTS.md` and `REVIEW.md`; this document describes the implementation and operator procedure, not a claim that every environment in the plan has been tested.
