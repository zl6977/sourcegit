## Defect Found (fixed in the working tree)

### `RepositoryNode` status badge generation guard lacks instance awareness

**File**: `src/ViewModels/RepositoryNode.cs:202-204`

**Problem**: `_lastStatusGeneration` (a plain `long`) is never reset on server restart.
The new server session starts its generation counter near 0, but the old value
(e.g. 50) remains, so all fresh statuses are silently discarded until the new
session's generation overtakes it (tens of change events).

**Impact**: Welcome page (Launcher) status badges for remote repositories stay
stale/null after a server restart. Main repository view (`Repository.cs`) is
unaffected (uses the correct instance-aware `RepositorySnapshotTracker`).

**Fix applied** (full §1 implementation, 3 files + test):
- `src/Models/RepositoryStatus.cs` — added `InstanceId` + `RepositoryId` properties
- `src/Commands/QueryRepositoryStatus.cs` — populates both from `client.InstanceId`
  and `handle.Id` (the transient lease)
- `src/ViewModels/RepositoryNode.cs` — `_lastStatus` is now
  `(string Instance, string Repository, long Generation)?`; generation compared
  only within same `(InstanceId, RepositoryId)` pair. A monotonically increasing
  query sequence (`Interlocked.Increment`) guards against out-of-order results;
  path change, cancellation, and instance mismatch all reject stale replies.
  Null results (query failure) also check sequence before clearing the badge.
- Test: `tests/SourceGit.GuiRemote.Tests/WelcomeStatusChecks.cs` covers all
  acceptance criteria from §1.

## Race Conditions (not fixed, by-design or out-of-scope)

### R1: Local path — concurrent startup and probe-failure service gap

**Severity**: Medium (development path only). The WSL/SSH deployment flow
uses per-build record paths and graceful shutdown; this does not apply there.

**What the lock already prevents**: The server holds an exclusive file lock
(`_recordPath + ".lock"`, `FileShare.None`) for its entire lifetime. The
`finally` block that deletes the record executes *before* the lock is released
(the `using` disposes at method exit, after the `finally`). Therefore a new
server using the same lock cannot publish its record while the old server
holds it. The described "old server deletes successor's record" race does not
occur in this flow. Lock contention does not queue a successor: opening the
exclusive FileStream fails with IOException, and RunAsync has no lock retry.
A minimal Windows same-process, two-handle check was actually executed by
the primary assistant through PowerShell: while the first FileStream held
FileShare.None, the second open immediately raised System.IO.IOException.
This was not executed or independently repeated by omp. It verifies the
observed same-process sharing conflict only; cross-process startup and full
deployment behavior were not tested by this check. Record ownership checks
remain a useful defensive measure.

**Remaining risks**:
1. **Concurrent `StartLocal`**: two managers (or a manager and a manual start)
   both see no record and each spawn a server process. One holds the lifetime
   lock; the competing process fails on lock acquisition. A manager may pick
   up the winning process's record, but unnecessary process starts and poorly
   diagnosed startup failures remain. This is not a successor overwrite.
2. **Probe failure as instance death**: a single transient `IOException` or
   `SocketException` during the probe triggers record deletion and a new
   server start. The new process fails on the old instance's lifetime lock,
   while StartLocal polls for a record that it deleted and eventually times
   out. The old instance may later idle out, but the failed new process does
   not automatically restart. Availability of an existing channel and the
   old instance's eventual exit depend on client activity and active tasks.

**Recommended fix**:
- Serialize `StartLocal`'s decision with a separate cross-process startup
  lock keyed by the canonical record path. The existing per-manager
  _connectGate is insufficient across managers/processes. Shared-read access
  to the server's lifetime lock is neither compatible with FileShare.None nor
  an exclusive decision lock.
- Probe with bounded retry (e.g. 3 attempts, 1 s backoff). If PID is alive
  but all probes fail, report a diagnosable error instead of deleting the
  record and spawning a duplicate.
- Before removing a dead/stale record, re-read its identity under the startup
  decision lock. If it changed or a probe returned another instance, restart
  discovery rather than deleting an unverified record.
- Keep the `File.Exists` guard in `finally` as defense-in-depth, but add a
  record-content check (`instanceId`/`processId` match) before deletion to
  protect against future refactoring that changes the ordering.

### R2: Client property references disposed client during upgrade gap

**Severity**: Minor window (up to 15 s), by-design gap.

**Location**: `ConnectionManager.cs:89-91` — old client disposed, but `Client`
property not nulled until the new connection is installed at line 108.

**Effect**: GUI code that touches `manager.Client` without gating on
`State`/`Connected` gets a disposed client during the "Starting" phase.
No data corruption; double-dispose is idempotent.

**Recommended fix**: Null `Client` when the upgrade is accepted.

### R3: Hung in-flight write blocks upgrade indefinitely

**Severity**: Liveness gap, low probability.

**Location**: `Program.cs:282` + `RepositoryService.cs:167` — registered writes
run with `CancellationToken.None`; `BeginShutdown` refuses while any operation
is `running`; `CancelOperation` explicitly refuses force-kill.

**Effect**: A hung git subprocess (stuck network fetch, wedged index lock)
blocks server upgrade until the process dies or the user kills the server.

**Recommended fix**: Add a configurable timeout (e.g. 10 min) on registered
operations; on expiry, terminate and reap the subprocess before recording a
terminal outcome and permitting shutdown. Merely marking a live process failed
would violate the active-operation shutdown guarantee.

## Verified Correct (detailed)

### 1. Generation / snapshot protection

- `RepositorySnapshotTracker.TryAccept` (`src/Remote/RepositorySnapshot.cs`):
  rejects cross-instance, cross-repo snapshots; compares generation only
  within same instance+repo.
- `Repository.cs:1164-1166` (branches), `:1367-1369` (working copy):
  guard applied before state mutation; null snapshot rejected.
- `RemoteWorkspace.cs:45-55`: event dedup generations cleared on instance change.
- `RepositoryService.cs:105-112` (`ReadSnapshotAsync`): `ChangeSequence`
  before/after check, 3 retries, then `IOException`.

### 2. Unified disconnection recovery

- All three write types (git/file/custom) funnel through
  `OperationTracker.RunAsync` (`modules/SourceGit.RemoteClient/OperationTracker.cs`).
- Recovery only issues `GetOperation` — never re-sends the original request.
- Server-side `OperationStore.Register` dedupes by owner-scoped operationId.
- InstanceId mismatch → short-circuit to "unknown" without querying.
- No automatic retry loop anywhere in `src/`.
- Fault-injection tests: dropped replies, channel close after send,
  acknowledgement loss — all confirm single execution.

### 3. Deployer separation and upgrade flow

- `ServerDeployer.cs` standalone component: "Never terminates a server".
- Install: SHA256-verified, immutable, versioned by Build+hash, under flock.
- Start: validates pid liveness + `/proc/pid/exe` + cmdline; detects upgrade
  by binary path (content change with same build id triggers it).
- Upgrade: authenticated channel → handshake (token via `SecureEquals`) →
  `ShutdownAsync` → `OperationStore.BeginShutdown` (atomic: refuses if
  accepted/running/waitingInteraction) → old server exits → client polls for
  new record → reconnect.
- Ownership/takeover gate prevents foreign-owner shutdown.

### 4. Git classification

- Client and server share `GitCommandPolicy` (single source, no divergence).
- `ls-remote` in unconditional Reads set.
- Branch/tag list forms: read-only. Mutation forms: write.
- Branch deletion: `DoesBranchExistOnRemote` returns `bool?` — `null`
  (query failure) aborts deletion; `false` → local-only cleanup; `true` →
  `push --delete`.
- `--output` on any read verb downgrades to write (prevents file writes).

### 5. Refs combined query lock

- `ReadSnapshotAsync` acquires the same per-common-directory `SemaphoreSlim(1)`
  as `ExecuteAsync`.
- Inner reads use `ExecuteCoreAsync` (no re-acquisition → no self-deadlock).
- `ChangeSequence` guard + retry (3x) prevents torn snapshots.
- Test: holds `for-each-ref`, fires `checkout --detach` mid-snapshot, asserts
  snapshot is not torn.

### 6. Directory browsing and handle lifecycle

- `RemoteDirectoryBrowser`: fully async, 200/page, incremental UI update,
  staleness guard after each page, per-window CTS cancelled on Close/Refresh.
- Cancellation: token plumbed through `ListDirectoryAsync` → `CallAsync` →
  `Protocol.WriteAsync`; 10-min timeout linked; fire-and-forget server
  `CancelRequest` on cancel.
- Cached opens, rebind and transient releases use `_repositoryGate`; direct
  transient opens do not acquire it. Instance-mismatch releases are skipped;
  disconnected releases are deferred to `_retiredHandles`. Unknown repository
  ids are no-ops, but repeated closes of a live shared id decrement references
  again: this is not full per-lease idempotency.
- `RebindAsync` preserves subscriptions for same instance, drains
  `_retiredHandles` matching the new client.
- GUI adapter regression tests cover concurrent rebind+release and
  cancellable multi-page listing.

### 1 Welcome 状态徽章的完整结果守卫

涉及 `RepositoryNode.cs`、`QueryRepositoryStatus.cs`、`RepositoryStatus.cs`。

- 保留当前 `InstanceId` 修复，增加 `RepositoryId`，代次仅在相同 `(InstanceId, RepositoryId)` 内比较。临时句柄完全释放后，同一服务器可能为同一路径创建新会话并从零开始计数。
- 查询开始时捕获节点路径、客户端实例及单调递增的查询序号。应用结果前检查路径未改变、序号仍为最新、未主动取消、远程连接仍有效，且结果实例等于当前连接实例。

- 失败返回 `null` 时也先检查查询序号，防止旧查询的失败清空新查询成功获得的徽章。将命令的取消令牌接入节点调用，不能只在调用前检查取消。

验收：旧实例 generation=50 后新实例 generation=0 被接受；新结果先返回、旧实例结果后返回时旧结果被拒绝；同实例会话重建后 generation=0 被接受；旧查询失败不得清空新徽章；取消和路径改变均不应用结果；本地仓库（InstanceId=null）行为不变，代次守卫不触发。

### 2 Local 启动流程与并发保护

涉及服务器 `Program.cs`、客户端 `ConnectionManager.cs`。

- 现有 `instanceLock`（`FileShare.None`，服务器 `RunAsync` 全程持有）防止使用同一锁路径的后继服务器在旧实例持锁期间发布记录。冲突的 `FileStream` 打开会失败，当前代码没有等待/重试；不能描述成两个服务器依次获得锁并覆盖记录。保留 `File.Exists` 守卫，增加 `InstanceId`/`ProcessId` 归属校验作为防御性措施；读取异常不应退化为无条件删除。
- **启动决策串行化**：使用独立于服务器生命周期锁的跨进程启动决策锁，以规范化记录路径为键，覆盖读取记录、探测、决定启动/升级和等待新记录的过程。同一个管理器的 `_connectGate` 已存在，但不能阻止两个管理器或 GUI 进程同时启动。不能用 shared-read 打开生命周期锁代替互斥。手动启动若不遵守决策锁，仍由服务器生命周期锁拒绝重复实例；客户端应检测子进程提前退出并收集失败诊断。
- **探测重试**：`ProbeAsync` 增加有限重试（3 次，1 s 退避）。PID 存活但所有探测失败时返回可诊断错误（包含 PID、端口、异常类型），不删除记录、不启动新进程。PID 存活本身不能证明进程是目标服务器，但单次探测失败也不能判定死亡。
- **陈旧记录清理**：客户端当前会在 build 不符、探测失败或实例不符后直接删除记录。改为在启动决策锁内重新读取，核对记录身份与最初读取值一致；只有确认陈旧且进程已退出时才清理。记录已变化或探测返回另一实例时重新发现，不删除未经验证的记录；活实例 build 不匹配按升级流程处理。重读再删除本身不是原子操作，该保证依赖参与客户端遵守同一决策锁，手动替换/外部编辑文件不在保证范围内。
- **活实例升级**：走认证握手 → 活动操作检查 → Shutdown → 确认旧实例退出 → 启动新实例。协议不匹配无法安全握手时报告需要人工处理，不能悄悄替换。
- 当前 Local 轮询为 100 ms、最多 100 次（约 10 秒），200 ms/15 秒是远程升级等待参数，不应混用。新增启动决策锁仅由客户端持有，服务器继续使用另一生命周期锁，不得启动后反向等待客户端持有的决策锁；获取决策锁及轮询均需支持取消和有限等待。等待时检测子进程提前退出，而不是只等记录超时。

验收：跨管理器、跨 GUI 进程并发连接均只执行一次实际启动，调用方复用同一实例；手动启动竞争导致锁冲突时快速报出诊断，不覆盖现有记录；首次探测失败、重试成功不启动新进程；PID 存活但连续探测失败不被替换（保留记录并返回诊断）；注入探测期间记录变化，客户端重新发现而不删除新记录；合法 Shutdown 后才启动后继实例；有活动写操作时升级拒绝且旧实例保留；取消等待及时返回。

### 3 临时句柄关闭失败与安全重试

涉及 `RemoteWorkspace.cs`、仓库打开/关闭协议及服务器引用计数。

- 不匹配实例的 `_retiredHandles` 当前已被清理，无需为不存在的跨实例积累另做修复。
- 匹配实例关闭失败时保留释放记录，无论客户端是否已经标记断线。重新绑定排水失败不得丢失当前条目；避免重新入队后在同一循环立即反复处理，可按队列初始长度或批次快照处理。
- **不能直接按共享 RepositoryId 自动重发 CloseRepository。** 当前 Close 每次减少引用；若首次关闭已执行但回复丢失，重试会减少另一使用者的引用。未知 id 的 no-op 不等于共享 id 的释放幂等。
- 推荐为每次成功 Open 返回独立 `LeaseId`，Close 按 LeaseId 原子释放一次；RepositoryId 继续用于查询与快照。服务端明确租约有效期、所属实例/所有者及重复释放语义，再启用关闭重试。该方案涉及协议兼容与客户端/服务器匹配发布。
- 协议暂不调整时，至少区分“确认未发送”和“执行结果未知”，保留未知释放诊断，不盲目重放；这只能改善可观测性，不能完全消除引用泄漏。

验收（LeaseId 方案实施后）：关闭回复丢失后重试仅释放一次；共享仓库的另一租约仍可查询。过渡方案验收：在线关闭失败保留待处理记录；排水失败不丢条目或忙循环；切换实例后旧租约被丢弃且不发送到新实例；重复 Close 同一 RepositoryId 的过度减少行为有诊断日志。

### 4 升级期间客户端生命周期

- Shutdown 被接受后，解绑旧客户端事件，在释放旧客户端前清除对外 `Client` 引用，并保持非 Connected 状态；Shutdown 被拒绝时保留可用旧客户端。
- 用局部变量保存旧实例身份，正确计算后续 `Connected` 的实例变更标记，不能因清空 `Client` 而丢失此信息。新客户端只在握手验证完成后安装。
- 调用方依然必须检查连接状态，并对断线/释放竞态做异常处理；将属性设为 null 不能取代生命周期检查。

验收：升级等待期间不暴露已释放对象；升级拒绝时原客户端仍能查询；新实例变更标记正确；升级失败不残留错误的 Connected 状态。

### 5 ReplyBarrier 队列保护和超时诊断

- 将普通事件与 ReplyBarrier 的入队抽为统一函数：递增积压计数、检查 4096 阈值、检查 TryWrite 返回值，失败时修正计数并触发断线/待请求失败流程。保持事件与有序回复之间的接收顺序。
- 无界 Channel 不会因为达到 4096 自动拒绝写入；该数值是应用保护阈值。改成有界队列时不得用丢弃策略丢掉 ReplyBarrier，也不得绕开此前事件直接完成成功回复。
- 保护阈值不能解决消费者回调永久阻塞。回调需要保持短时、非阻塞；客户端 Dispose 等待事件消费任务的行为也需单独检查，避免关闭被回调卡住。
- 在 `CallAsync` 中仅当内部期限到期、且调用者和连接生命周期令牌均未取消时，转换为包含方法名和期限的 `TimeoutException`。保留用户取消与断线的原始语义。
- 浏览器显示明确的超时提示；写操作 RPC 超时不等于服务端写入失败，不自动重发，仍应保留结果未知及操作查询恢复语义。

验收：持续压入 ReplyBarrier 同样触发积压保护；队列关闭时请求及时失败；[回归保护] 输出事件先于写操作成功回复交付（现有 `_orderedReplies` 机制保证）；目录浏览超时显示诊断，用户关闭不报错；写操作 RPC 超时不重复执行。

### 6 写操作期限与升级活性

- 区分 RPC 等待期限和服务端操作执行期限。客户端超时/断线不能自动取消持久写操作；服务端使用独立配置的操作期限，不绑定连接令牌。默认值应根据长时间 clone/fetch 和自定义命令评估，10 分钟仅是候选值。
- 到期后先进入仍阻止 Shutdown 的终止中状态，停止进程树、等待退出及输出管道收尾，再发布终态并释放仓库锁。终止失败时继续阻止升级并报告原因，不能只改 State。
- 若新增 `terminating` 等非终态，必须同步修改 `OperationStore.BeginShutdown`、服务器 idle-exit、所有者接管的活动检查、File RPC 的等待循环及客户端 `OperationTracker` 轮询；这些路径目前硬编码现有状态集合。建议抽取统一的非终态判定，确保终止中不被当成完成或未知，也不能被接管或放行关闭。
- 超时终止和正常完成必须由同一个操作状态机协调：使用锁或 CAS 原子决定哪条路径获得最终结果发布权，不允许终止路径把已完成操作改回非终态，也不能在正常完成路径未确认清理完成时覆盖终止状态。单独增加 `volatile bool` 并“检查后写入”不保证原子性；不要因期限刚到就把实际上已完成的操作误报成失败。
- 当前 Core 在输入写入后才注册取消回调，且自定义命令使用默认令牌。实现期限时需覆盖锁等待、标准输入阻塞、Git/自定义子进程与输出收尾；同步文件系统操作不能假定 CancellationToken 能立即中断。
- 强制终止不能宣称回滚成功。提示可能的部分写入和锁文件，刷新仓库状态；不要自动删除 index.lock 或其他锁文件，不自动重试原写请求。
- 正常网络断线恢复继续保持“只查操作结果、不重发”。必要时先提供明确的超时告警与诊断，再发布可配置终止能力。

验收：正常长任务在配置范围内完成；挂起子进程到期退出后才能升级；终止失败仍拒绝 Shutdown；在正常完成与超时同时发生的屏障测试中只发布一次最终结果、无终态回退、无提前释放锁；断线不触发终止；交互等待与执行期限边界明确；超时后的未知/部分结果不会被展示为已回滚。

### 7 大目录分页性能

- 当前每页全量枚举并排序是性能问题，不是结果错误。按需增加短生命周期的目录快照游标：首次构建排序列表，后续页从同一快照读取，设置条目数/内存上限、TTL，并在取消、断线或完成后回收。
- 明确目录在分页期间变化的语义，避免使用不同时间的排序结果产生重复或漏项；游标失效时提示刷新，不静默拼接两份快照。
- 不建议在本轮正确性修复中顺带引入长期全局目录缓存。

验收：大目录整轮分页不重复全量排序；分页期间变化的行为可预测；取消与游标失效能释放资源；内存有明确上限。

##### A. 连接与 Dispose 生命周期（#2，先于等待预算调整）

- `DisposeAsync` 先原子关闭新的连接入口并取消管理器 lifetime，协调 `_connectGate` 下的在途连接退出，然后清空公开 Client、解绑事件，释放 client/tunnel/launcher 和 CTS。检查 ConnectAsync 在等待 gate 之前、获得 gate 之后以及安装 Client 之前的 disposed/cancellation 守卫，防止释放完成后重新发布 Connected。
- `LocalServerLauncher` 的启动进程、PID、输出任务应由本次启动持有稳定的局部引用；释放方不能在启动/退出通知使用句柄期间 Dispose 它。单独 catch `_process.HasExited` 的 ObjectDisposedException 只能隐藏一处症状，不能覆盖 Id、ExitCode、WaitForExitAsync、输出流及 CTS 的同类访问。
- 不把未知启动错误都转成取消，不在异常后继续轮询已释放对象。主动释放引发的在途取消与释放后新调用的 ObjectDisposedException 要有明确契约。协调时复核事件回调/重连任务的重入路径，避免持锁等待自身或 Dispose 与 Connect 相互等待。
- 用按连接代次管理的共享恢复完成信号替换 WaitForRecoveredClient 的 100ms 状态循环；已连接时立即返回，新连接安装完成时通知，Failed/Dispose 结束对应等待。单个调用方取消不取消其他操作的恢复等待，旧代次通知不能唤醒新代次。
- 保留服务器独立生命周期：释放 launcher 的本地句柄不能杀死已启动服务器，也不能取消服务器中已登记的持久写操作。

验收：用屏障分别停在启动前、进程启动后/首次 HasExited 前、记录已读/Client 安装前，再并发 Dispose；在途连接按约定结束，释放后不安装 Client、不出现 Connected、不泄漏 launcher/tunnel 句柄。重复 Dispose 与释放后 Connect 行为稳定；无未处理的句柄释放异常、无死锁。服务器已启动时仍能独立完成操作并按 idle grace 退出。先跑定向故障用例，再跑 Local 启动和现有升级生命周期回归。

##### B. 决策锁等待预算（#1）

- 将默认获取 `.startup.lock` 的等待预算设为 60 秒，独立于探测每次 3 秒、Shutdown+旧进程退出共用 10 秒、ready 发布等待 10 秒等阶段预算；等待者到期只报告锁等待失败，不能删除记录、启动竞争实例或终止持锁者。
- 使用单调时钟计算等待期限；等待/必要退避期间响应调用方取消。优先按 G 评估能真正跨 GUI 进程通知的锁机制；在该机制落实前，不能删除 FileStream 独占锁，仅保留有界、低频退避作为兼容等待。诊断包含“startup decision lock”、实际等待预算与规范化记录路径，不暴露 token。仅在竞争等待时输出必要诊断。
- 60 秒是有界等待的默认策略，不是所有文件系统 I/O、记录变化发现循环和可注入 probe 的绝对持锁上限。避免把原审查的 ~30 秒描述写进代码或部署保证；若未来要求整个启动决策的严格总期限，应另行设计，明确 Shutdown 已接受之后超时的恢复语义。
- 提供内部时间参数或时钟注入用于快速故障测试，生产默认仍为 60 秒；验收至少保留一项真实跨进程、等待超过原 15 秒预算的测试，不能全部依赖缩短时间参数证明。

验收：持锁者在受控慢启动/升级期间占锁超过 15 秒、在新预算内完成，第二管理器继续发现并复用获胜实例，未多启动进程。不同 GUI owner 仍按已有所有权规则拒绝，不因锁预算扩大而绕过认证。调用方取消及时返回；超过新预算的等待保留持锁实例和记录并给出明确诊断。调整原 15 秒超时用例及文档中的参数，不修改服务器生命周期锁。

##### C. Probe 契约与重试分类（#3）

- 默认 probe 使用自己的 3 秒 CTS，当前主要异常是 IOException、SocketException 和 OperationCanceledException；注入委托抛任意异常不应天然意味着需要重试。
- 保持已知暂态网络错误的三次有限重试；对独立 TimeoutException 明确支持重试。调用方 cancellation 已触发时立即传播取消，不退避。认证/协议不匹配在现有 IOException 路径中仍必须保留活 PID/记录，不自动替换实例。
- ArgumentException、InvalidOperationException 等非暂态异常默认直接报告原始原因；不通过 catch(Exception) 吞掉编程错误或盲目重试。捕获范围要覆盖探测本身，避免把随后记录重读/校验失败误归类为网络探测失败；记录身份变化继续走重新发现。

验收：注入 IOException/SocketException/独立 TimeoutException 后能按约定重试成功；连续三次失败有次数、异常类型、PID/端口诊断且不删除活实例记录。主动取消没有后续探测/退避；非暂态异常仅调用一次并保留原始类型/原因；记录变化与读取失败分别走既定发现/报告路径。

##### D. RPC deadline 与断线同时发生（#4）

- 先复核 ReadLoop/Dispose 的 `IsDisconnected`、`_lifetime.Cancel()`、待请求失败发布之间的顺序。审查描述的是竞态窗口；不能仅看到 `!IsDisconnected` 就承诺所有同时发生的断线都必须转换成 TimeoutException。
- 采用明确的诊断规则：异常分类时调用方令牌已取消则保留主动取消；连接 lifetime 已取消或请求已有连接失败结果则保留连接失败语义；仅内部 deadline 已触发且上述取消未触发时，转换成包含方法名/期限的 TimeoutException。IsDisconnected 作为状态快照不额外否决最后一种转换；移除条件之前确认与生命周期发布的一致性，必要时统一失败原因的发布。
- 这是取消诊断的规则，不宣称能从独立 bool 快照推断两个异步事件的物理先后。若采用固定的首次完成结果，需用一个原子完成点记录原因，不能靠多个状态的“检查后写入”制造确定性。
- 保留写操作结果未知与恢复机制：不重发 ExecuteGit/File/Custom；若提交 RPC 超时，OperationTracker 对原 operation id 做一次结果确认；已登记则转入 WaitOperation，断线后恢复同一 id 的等待；unknown 按 G 的结果未知契约保留待确认记录，不能视为未执行。普通 RPC deadline 与长等待契约分开，不能因普通 RPC 到期而固定周期重发 WaitOperation。

验收：以屏障控制 deadline 到期后状态已置断线但 lifetime 尚未取消、lifetime 先取消、调用方先取消、连接失败已完成请求等路径；分别验证规定的异常类型与诊断。正常超时、正常断线和主动取消回归不变；写请求只提交一次，原 id 保留，重连继续仅查结果。不能用反复 sleep 碰概率代替屏障验证。

##### E. Shutdown 的终止清理诊断（#6）

- 在现有 operation store admission gate 内检查活动操作并生成拒绝消息；仍阻止 accepted/running/waitingInteraction/terminating 全部状态，且拒绝时不关闭操作入口。
- 若有 terminating，消息明确表示“终止/清理仍未完成”，建议通过 GetOperation 查询对应操作；可提供有界的 id/状态摘要。不要复制未裁剪的输出、环境数据或 helper token，也不要为改善消息引入新的全局→进程锁等待。
- running/等待交互仍使用活动操作拒绝；详细的最新清理失败原因继续通过 OperationInfo.Error 获取。诊断变化不改变超时、重试、升级或所有权策略。

验收：running、waitingInteraction 和注入 kill/cleanup 失败的 terminating 分别拒绝 Shutdown，且消息正确区分；terminating 完成清理前拒绝，清理后成功。混合多个活动状态时摘要有明确长度上限。拒绝后原客户端仍可 GetOperation、查询仓库和完成原操作；不泄露 helper/连接凭据。

##### F. 仓库锁释放与 Complete 顺序（#5）

- 保留“进程树和输出清理完成 → 释放 common-directory 锁 → execute 返回 → Complete 发布终态”的现有顺序。清理后的新仓库操作可在上一操作仍显示 running/terminating 的短窗口内开始；Shutdown、idle exit 和 owner takeover 仍因上一操作的非终态而拒绝。
- 原 §6 的“发布终态并释放锁”应按两项职责解释，不能表述成两个动作原子同时发生。安全要求是进程/文件执行未收尾时不释放仓库锁，未发布终态时不放行服务器关闭；不是强制把 OperationStore 引入 Core 并延长仓库锁直至网络完成事件送达。
- 补充确定性顺序测试：暂停在 repository 执行返回之后、Complete 之前，确认后续仓库任务可获得锁，而 Shutdown/idle/takeover 仍被拒绝；释放屏障后仅发布一次终态。继续覆盖 kill 失败时锁不能提前释放。

验收：清理前无法获取相同 common-directory 的锁；清理后/Complete 前不放行服务器关闭，但不把正常排队仓库操作当成泄漏或并发写入缺陷；终态发布不回退。若以后业务需要“终态可见后才能接受下一仓库写入”，另立协议/调度需求，不在本次 minor 修复中暗中改变。

**事件驱动的关键约束与验收**：

- 完成任务使用 RunContinuationsAsynchronously，并在状态/结果被保存之后通知；等待者取消只能取消自己的等待，不能取消共享完成源。终态只发布一次，terminating 保持活动，清理失败继续阻止升级。
- OperationCompleted 必须在提交/首次权威查询之前订阅，保持原有输出与 ReplyBarrier 顺序；不能因事件先到就让成功结果越过之前的输出。回调只完成信号，不等待 UI 或重连。重连先订阅再查结果，检查 channel/instance/operation 身份并清理旧订阅。

- **P2 等待容量与取消**：WaitOperation 使用独立于普通 16 个执行槽和现有约 128 个挂起请求限制的有界等待配额，设置每 channel 与全局上限；实现时记录具体默认值及容量测试依据。超额立即返回明确容量错误，不自动高频重试；Ping、SubmitInteraction、CancelRequest 和结果查询保持可用。客户端同一 channel/instance/operation 的等待共享远端请求时，本地取消只移除自身，最后一个等待者离开才取消远端等待。取消、断线、终态及发送失败均释放名额。测试满额时普通请求/交互仍能完成，反复取消和重连不积累等待者。
- **P2 结果未知**：提交超时后，原请求可能仍在服务端执行槽中排队；一次查询返回 unknown 不证明未执行。保留原实例、operation id 和待确认记录，向调用方明确返回“结果未知”，禁止自动重发写请求。后续同实例的登记/完成通知、重连或用户显式查询可更新记录，不新增周期查询。实例变化后保留未知结果供人工核对，不跨实例等待旧 id。若要求原调用在这种情形自动等到终态，应先定义提交登记屏障或可靠的登记等待协议，不能声称 unknown 即返已提供此保证。用屏障测试“提交仍排队 → 查询 unknown → 原操作登记执行”，验证只执行一次且待确认记录不丢失。
- **P3 统一定时契约**：TTL、idle、debounce、下一次 fetch 的相对期限使用单调时钟；重设/取消递增代次，旧回调即使已排队也不能执行过时动作。回调在所属同步边界内重新验证期限和条件，同类工作不重入；Dispose 后不得重新安排任务，等待回调收尾不能持锁互等。可控时钟测试重设与触发同刻、旧回调晚到、时钟调整和关闭竞态；无需为复用引入大型调度框架。
- **P3 Watcher 最大延迟**：debounce 记录首个 dirty 时间及最大合并窗口；持续事件不能无限推迟刷新。锁持有期间保留 dirty，解锁后安排刷新，最大延迟不绕过锁。测试持续事件流仍产生刷新、刷新期间的新事件进入下一批。
- **P3 fetch 受阻恢复**：订阅弹窗可用性、index.lock 删除/重命名和 remote 配置变化，采用订阅后检查避免丢唤醒。禁用时取消调度，重新启用或间隔改变时按新周期计时；到期因弹窗/锁受阻时保留到期状态，条件恢复后只执行一次；无可抓取 remote 时暂停，出现可用 remote 后重算，已到期则执行一次。完成后从完成时间安排下一周期，不补跑积压次数。这是相对当前弹窗阻塞时更新 _lastFetchTime 的明确语义调整，需测试并记录。不可监听路径复用明确的 degraded 通知，不另加常态 5s 检查；关闭时解除所有订阅。
- **P0 平台可行性门槛**：记录 Windows Job 通知注册时机和空树核验方案；Linux 明确通知来源、收养后代的回收归属、与 .NET Process root 等待的协调及最低支持环境。原型覆盖先退出后订阅、root 先退出、后代保留/关闭管道但仍存活、并发回收和通知设施失败。bootstrap 另验端点提前建立、旧实例退出身份、ready/退出竞态、SSH 断开及端点清理；锁原型验证与既有 FileShare.None 的跨版本互斥。证据充分才进入 P5/P6 替换；未验证平台保留现有安全机制并列为未完成，不能宣称已取消轮询。
- 连接恢复信号按代次区分：多个操作可共同等待一次恢复；其中一个调用方取消不得取消其他等待。Dispose 结束所有挂起等待，不在已关闭管理器上发 Connected。超时/Failed 与 Connected 同时发生有确定的完成规则。
- 文件事件只是唤醒信号。订阅后检查、通知后重读身份、事件丢失/溢出及发布早于订阅等路径均需故障注入；ready 与 early exit 同时发生时完成一次，不接受错误 PID/实例的记录。
- 进程树通知测试继续包含 root 先退出、后代保留管道、后代关闭管道但仍存活、终止失败与多操作并发 reap。新方案若无法证明整个 contained tree 已退出，就不允许用 root 的 Exited 事件直接放行锁/Shutdown。
- GUI watcher 测试包含 burst 合并、锁期间事件、解锁即唤醒、刷新期间新事件、Dispose 与 callback 并发；正常远程仓库空闲时没有 100ms 状态检查，失效本地 watcher 的低频降级有明确开关与诊断。
- 协议测试统计请求：正常活动操作等待期间不再每 150ms 发 GetOperation；完成事件先于提交回复、断线/重连、结果早已完成、事件发送失败都不漏终态，不重复写请求。File RPC 不再每 20ms 检查 State，等待任务无空闲唤醒。
- TTL/idle 测试使用可控时钟验证创建、提前释放、重设期限、过期与 Dispose，并验证空集合/有活动任务时没有持续周期扫描。心跳、业务 fetch、UI 时间显示和必要失败退避分别记录，不以“项目中仍有 Timer”判定改造失败。

##### H. 实施前必须明确的事件归属与失败规则

本节补充 G 的落地约束，仍按 P0–P8 实施，不新增一套阶段编号。

| 所属阶段 | 信号与权威状态 | 生命周期与失败处理 |
|---|---|---|
| P1 | 恢复完成信号；已安装且验证过的 Client 为依据 | Manager 持有恢复代次，调用方只取消自己的等待；主动升级关闭旧 channel 与非预期断线区分，避免旧 EOF 触发第二个重连/部署流程 |
| P2 | Completion / WaitOperation；OperationStore 终态为依据 | Store 持有完成源，channel 持有等待配额；ReplyBarrier 保持输出先于结果。事件消费者缓慢不得无限累积队列或占住所有查询槽 |
| P3 | 偏好、页面可用性、文件锁、remote 变更与任务完成；执行前重读条件 | Repository 持有订阅和调度；timer 只向 UI 投递，UI 检查代次后启动。关闭页面取消本地 fetch、观察任务收尾并解除订阅，不同步阻塞 UI 等待捕获 UI 的 continuation |
| P4/P5 | ready / 退出通知；认证记录与稳定进程身份为依据 | 启动组件持有输出消费者、进程句柄与通知端点；通知只唤醒校验。取消或超时不等于服务端未启动，不删除未确认归属的记录，不启动竞争实例 |
| P6 | 平台 containment 通知；整棵受管进程树已退出并完成回收为依据 | 每个操作有独立 containment 和回收归属；通知缺失、错误或清理失败保持 terminating 与仓库锁，诊断后按失败退避处理，不伪造终态 |

**P2 容量和未知结果的补充交付**：

- 当前等待配额 64/channel、1024/global 作为本轮初始值，补测全局饱和、多 channel、断线与发送失败回收；记录峰值等待数和占用。客户端同一操作的多个观察者是否共享请求必须有实现证据，不能仅凭服务端共享 Completion 宣称已经合并远端请求。
- 待确认记录定义状态转换：提交待确认 → 已登记等待 → 已终态；或实例变化 → 结果未知、供人工核对。定义记录的持有者、数量限制和显式清除方式；容量不足在提交写请求前报告，不能静默淘汰未知结果。操作关闭、观察者取消与服务器重启均不自动重发原写请求。
- 用同一组屏障测试完成先于回复、输出拥塞、超时与断线、未知后延迟登记；检查终态、输出顺序、请求次数和配额回收，避免只断言“不再出现 Delay”。

**P3 本地 fetch 的具体接线与状态规则**：

- `LauncherPage.Popup` 替换和 `Popup.InProgress` 改变都要通知；Repository 打开早于页面挂接时，挂接完成也须重查。仅订阅 Popup 属性会漏掉同一弹窗从忙到闲的变化。
- remote 列表替换与单个 `DisableAutoFetch` 切换都触发重查；index.lock 使用当前 worktree 的 GitDir 路径，覆盖删除、重命名和通知源恢复。Watcher 原有忽略 `.lock` 的规则不能吞掉此信号；订阅完成后立即读取条件。
- 状态最少区分禁用、等待期限、已到期受阻、运行中、已关闭。弹窗/锁解除与计时同时到达只启动一个任务；执行前重读锁是保守检查，无法禁止外部 Git 随后创建锁，实际命令失败仍按失败结果处理。
- 手动 fetch 成功调用 MarkFetched 时重设下一期限；自动任务成功或失败都从收尾时间安排下一周期，保留失败日志，避免失败后立即重复触发。间隔非正值须明确处理并诊断，不能产生零期限忙循环。页面关闭取消的是本地任务，远程已登记持久写仍遵循 P2 的独立生命周期。
- 增加事件接线测试及可控时钟测试：页面晚挂接、同一弹窗忙闲切换、worktree 锁、remote 禁用/新增、手动 fetch、任务失败、运行中改偏好、关闭后晚到回调。纯调度器测试不能代替实际接线验收。

**P0/P5/P6 原型与降级决定**：每份平台结论写明支持环境、通知注册点、身份核验、资源释放、故障证据，以及“采用 / 保留现有安全路径 / 不支持”的决定。bootstrap 通知端点限制为当前用户可访问，绑定本次启动身份，不输出认证 token；SSH 断开后的服务器归属、端点回收和再次连接复用均须验证。可靠阻塞等待可占用数量受限且可取消的专用等待资源，但不能转成线程池中的无限检查循环。未通过机制门槛的项保持未完成，交付独立已验证部分时明确列出保留循环及下一步，不降低整树退出或跨版本互斥保证。

**P6 分平台机制与剩余门槛**：

- Windows 使用稳定的进程句柄注册退出等待，并在成员退出通知后重新查询 Job 成员；以权威 ActiveProcesses 为零确认空树。普通 Job completion-port 消息不能作为唯一完成依据，[Microsoft Job 文档](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)明确其投递通常不保证。成员快照须处理缓冲区不足、进程已退出和 PID 复用；注册后再次核验，旧回调不能访问已释放 Job。根进程退出后才开始等待也必须识别仍存活的后代，以及之后创建的孙进程。
- Windows 实际 RunAsync 中“根退出且后代关闭管道”的锁/终态屏障和成员查询/扩容、部分注册故障、取消/Dispose 并发及资源峰值已验证，见末尾 P6 Windows 增量。原型句柄和实际管线证据分别维护。containment 紧随 Process.Start 才绑定 Job；确认退出的范围仅限该 Job 已收纳成员，绑定前创建的后代不在已验证保证中，退出通知改造未扩大这一原有边界。
- Linux 已采用每成员稳定 pidfd + waitid(P_PIDFD)；先由 .NET 回收 root，再按 pidfd 回收本操作组内已收养后代，不使用全局 waitpid(-1) 或负组号回收。只在注册及成员退出/HUP 后核验成员，kill(-pgid, 0) 的 ESRCH 才证明空组；管道 EOF 和 root 退出均不单独放行。最低内核 **5.4**，x64 已在 WSL 验证，arm64 尚未实机验收。远程环境预检及启动 Git 前的原生能力检查明确拒绝不支持环境。
- 两平台正常路径均不恢复周期扫描。Linux 最多 64 个专用阻塞等待资源、每组 4096 个活成员监听，另受宿主 FD/进程上限约束；取消通过 pipe 唤醒，资源不足/通知失败保留清理责任。已收养僵尸逐个回收，不因活成员预算导致退出树永久无法清理。真实清理设施失败才使用 500ms 起、封顶 5s 的退避，整个期间保持 terminating 和仓库锁。Linux 64 等待资源饱和、注册/身份/回收故障、实际 4096/4097 活成员压力及 Windows 查询/注册故障均已有定向证据，最终同包和受控性能继续归 P8。

**剩余工作的验收顺序**：

1. P2 的 Windows 定向门槛已有证据；P8 使用最终匹配包复验跨平台行为。保持写操作安全验收，不能仅凭 RPC 次数减少交付。
2. P3 Repository/头像及 P5 错身份、丢 ready、ready/退出竞态和取消窗口已有定向证据；继续补 Watcher 其余故障、实际 SSH 生命周期与跨环境行为。SIGKILL 端点已按 PID/start、UID、私有权限和独占锁核验回收；未知/legacy 归属保留，不删除其他活动启动器端点。
3. 分平台完成 P6；P4 Windows 兼容锁保留单独结论及迁移门槛。每个残留轮询登记位置、触发条件、间隔/上限、保留原因和删除所需证据。
4. 产品代码及协议稳定后再制作 P8 最终匹配包、执行回归和受控性能对比；开发 bootstrap 包及旧协议包均不能充当最终包证据。

每个阶段分别标注“已实现、已验证、未验证、允许保留”，结项同时要求实现与必要验收完成；历史失败和重跑证据保留。持续观测和资源限制随事件改造一起验收，避免减少轮询后引入无界等待者或句柄占用。

**可观测性**：为保留退避/degraded 模式记录触发原因、进入/恢复时间、重试次数和下次期限；重复错误合并，限制日志大小。P8 审计同时包含等待者/待确认记录、事件队列和句柄峰值，防止 CPU 减少但内存或资源占用无界增长。性能对比预先固定观察时长、重复次数与负载，分别报告空闲和活动样本；至少记录操作可见延迟的中位数和高分位数，不能用一次结果概括所有场景。

**统一交付要求（顺序与状态见 P0–P8 表）**：

- P1–P7 每项先跑对应故障/竞态测试，再跑受影响的已有回归；证据关联编号，记录实际日志与退出码。验证通过的独立改造可先交付，不等待所有平台原型结束。
- P8 完成 Server/Remote/GUI 构建及完整 Remote、GUI 适配器、Local 启动、匹配最终包的 WSL 回归；对照 P0 基线测量并审计剩余轮询，更新 IMPLEMENTATION_STATUS、TEST_RESULTS、DEPLOYMENT 的协议、预算、通知/取消语义和保留项。
- 未执行的 SSH、实际 GUI 窗口、Windows AOT、arm64 继续列为未验证；不能用 WSL 通过替代 P5 的 SSH 独立生命周期验证。IPC ACK 独立后续设计，不纳入本轮验收。
**最终删除清单与保留边界**：

- 必须删除：OperationTracker 定期 GetOperation、File RPC 状态循环、恢复 Client 状态循环、本地 child/record 和旧 PID 轮询、远程升级重复 StartAsync、shell 记录出现轮询、常态进程树定期扫描、目录 TTL 每秒全量扫描、channel/idle 每秒状态扫描、Watcher 100ms dirty 标志扫描、头像队列空闲 Sleep、本地 fetch 每 5s 检查条件。
- 改为一次性期限：操作超时、ready/退出等待超时、快照最早到期、channel 失活/idle、文件事件 debounce、下一次 fetch。没有待办事项就不唤醒；定时器到期不表示任务已成功完成。
- 允许保留：10s 心跳、用户指定 fetch 周期、必要 UI 时间显示；真实网络/探测/清理失败后的取消感知退避；不可监听文件系统的明确 degraded 刷新。它们有业务期限或真实失败作为触发条件，不掩盖正常路径状态轮询。
- 决策锁暂留例外：先实现同一锁语义的操作系统阻塞等待；若无法与现有 FileShare.None 决策锁保持跨进程兼容，则在该迁移完成前允许取消感知退避（250ms → 500ms → 1s 上限，仍有 60s 获取期限）。这一项单独标记保留原因，不把它描述为已去除；不能换成进程内 semaphore，也不能让旧/新客户端分别用不同互斥机制悄悄失去协调。
- 平台通知不可靠时：先修复通知注册/所有权和重读验证；若只能安全依靠轮询，明确留下待完成项和限制，不降低安全保证来满足表面上的“零 Delay”。

**结项证据补充**：静态检查列出的每个正常状态循环已删除；请求统计证明操作等待不定期发 GetOperation、远程升级不重复发启动脚本；空闲状态无 dirty/TTL/idle 的固定频率唤醒。丢 ready、通知先到、通知设施失败、完成广播丢失、SSH 断开、取消/Dispose 等故障均有明确超时或恢复结果。保留项按上述边界逐条列出，不以“没有 Task.Delay 字样”替代行为验证。

**性能验证与收益边界**：

- 预期收益是减少空闲 CPU/线程唤醒、重复 RPC/序列化、Linux 进程扫描，以及等待下一个轮询周期的响应延迟；不宣称 Git 命令本身执行得更快。现有 150ms 操作查询约为每个活动操作每秒 6.7 次、20ms 进程树检查约为每秒 50 次，这是配置推算，实际请求/扫描次数需实测。
